Overview

1Scope & the editor loop

The editor lets a plugin author edit both halves of an installed debug plugin in place, push changes to the running Runtime without reinstalling, and watch backend print output from the chat they opened the editor in.

From the original user story:

  • A plugin has states: debug / release.
  • Only the author can install a debug plugin; it never appears in the public marketplace.
  • An installed debug plugin shows an Edit button.
  • The editor renders in two places: the right-hand panel (where the marketplace lives) and a separate window.
  • The editor is two text fields (Lua, JS) plus a debug console that prints backend output from the chat the editor was opened from.

Nothing about state inspection, multi-file plugins, or a build step is in scope. Code is exactly two files: one client, one server. State inspection is in scope: the editor has an editable JSON state panel for the chat it was opened from (§7, §12). State history, diffing and breakpoints are not.

Decision · mapper in integration-service

3Identity model

The core stores one pure UUID per user and nothing else. The uuid ↔ mxid mapper lives in integration-service — the one component that already speaks Matrix. An MXID appears on exactly twothree hops: inbound (Dendrite → Gateway) and, outbound (integration → Dendrite), and display enrichment (Gateway → client, so the UI can render @localpart).

The :domain suffix cannot leave the Matrix wire protocol without forking away from federation — it is structural (event sender, room membership, routing). The domain is fixed to one constant and simply not rendered; Element already speaks MXIDs, so showing @user_id is a trim, not a new identifier.

internal_uuid

The foreign key in every Fstick service: plugins.author_id, installations.installed_by, branch owner. Never leaves the backend, never reaches Dendrite.Opaque to the client: it may appear in API responses and in GET /api/v1/me so the frontend can compare ids, but it is never rendered and never reaches Dendrite.

MXID

@ilya:fstick.local → @ilya
Matrix's own id

Dendrite's: sender, membership, tokens, event push. Frontend renders the localpart only; the domain is one fixed constant. The Matrix display name is untouched — a label, not an identifier.

The mapper

  • Table in integration-service: internal_uuid (PK) ↔ mxid (unique). Bidirectional. No handle, no profile layer.
  • POST /api/v1/identity/resolve  { mxid } → { internal_uuid } — create-or-return, idempotent. This is where a user's internal_uuid is minted, on first contact.
  • GET /api/v1/identity/{internal_uuid}  → { mxid } — the reverse, for outbound push. Batch variant for member lists. Batch variants in both directions: resolve-batch (mxid → uuid: member lists) and lookup-batch (uuid → mxid: Gateway response enrichment).
  • Gateway calls resolve to turn the X-User-Id Dendrite gave it (an MXID) into internal_uuid, then forwards that. Result cached in-process — the binding never changes, so the cache is an LRU with no invalidation. X-User-Matrix-Id is not propagated; nothing past the Gateway needs it. The Gateway also keeps the reverse map (uuid → mxid) and uses it to enrich responses on the way out.
  • registry.plugins.author_id = internal_uuid (column is already UUID). Delete resolveAuthorId() / nameUUIDFromBytes.
  • GET /api/v1/me → { internal_uuid, mxid } — served by the Gateway from its mapper cache; the frontend's only source for its own internal_uuid (§12).
  • Installation-service keeps calling integration for chat-membership checks, now passing internal_uuid; integration maps it to the MXID before asking Dendrite.

No migration

There is no production database and no legacy plugin. Schemas are rewritten in place — plugins.author_id holds an internal_uuid from the first row, installations.installed_by becomes UUID — and local volumes are recreated. No backfill, no compatibility paths.

Why Postgres, not just Redis

Gateway keeps a Redis or in-process cache either way. The question is the system of record, and that has to be Postgres:

  • It is source of truth, not derived data. Every plugins.author_id and installations.installed_by FK is an internal_uuid that only has meaning through this table. A cache you can rebuild from upstream; this table is upstream. Lose it to an eviction or a flush and every ownership record is orphaned.
  • Durability. Redis persistence (RDB/AOF) is lossy by design — snapshot intervals, fsync windows. Postgres gives real ACID + WAL: a committed identity stays committed.
  • Atomic idempotency. resolve must mint exactly one internal_uuid even when the same new user fires two requests in parallel. UNIQUE(mxid) + INSERT … ON CONFLICT DO NOTHING RETURNING does this in one statement. In Redis it is a hand-rolled SETNX/Lua dance with edge cases.
  • Queries. First-seen audit, admin lookups, batch member resolution, later handle history if it ever comes back — all relational. Redis answers exact-key GET and nothing else without hand-built secondary indexes.

So: Postgres is the system of record; Redis (or the Gateway's own map) is an optional read cache in front of it — invalidation-free, because the mapping is immutable.

Cost

integration-service is stateless today (a pure Dendrite ACL — no datasource). This gives it its first table. And the Gateway now depends on integration to authorise any uncached request: cached users survive an integration outage, brand-new users get 503. integration is already on the critical path (installation-service calls it for membership), so this is not a new failure class — but it is a wider blast radius. See §13.

4Versioning: branches & content-addressed blobs

  • Exactly two blobs per branch (client + server). The client-supplied filename is discarded.
  • The dev branch's blob shas are its HEAD; a save replaces them (old blobs become GC candidates — see §13).
  • An installation references a branch. A debug install points at the dev branch and follows its shas.   • Moderator role: a user is a moderator if and only if their internal_uuid is in registry.moderators. The first rows are seeded from config; after that, existing moderators grant the role. Registry checks it on every moderation endpoint.

Phase 2, when diff / revert / history is wanted: add a commits table. Blobs are already content-addressed, so it lands with no data migration.

Decision · explicit actions

5Moderation lifecycle

The author works on the dev branch. Publishing cuts a candidate branch into a review queue. A rejection (moderator) or a cancellation (author) leaves a dead branch — the author goes back to the dev branch and publishes again.

On reject

  • Who may reject: any moderator from WAITING_APPROVE; from APPROVING only the moderator who claimed it (same rule as approve).
  • Branch status = REJECTED, retained (hidden, never in the queue, never installable).
  • plugins.last_rejection = { reason, at, semver, branch_id } — so the UI shows "needs changes" without scanning chat.
  • A plugin_moderation_log row is appended.
  • A message is sent to the author in a system room (“Fstick Developer”) via Integration — delivery, not the record of truth.

On cancel

  • The author withdraws their own candidate from WAITING_APPROVE or APPROVING: POST /plugins/{id}/branches/{bid}/cancel.
  • Branch status = CANCELLED, retained as a tombstone (hidden, not in the queue, not installable).
  • No last_rejection, no bot-room message — nothing was wrong. A plugin_moderation_log row is still appended for the trail.
  • If a moderator had already claimed it (APPROVING), it just disappears from their queue.
Guard

POST /publish returns 409 if the plugin already has a non-terminal candidate (WAITING_APPROVE or APPROVING). One open candidate at a time — a rejection or a cancellation clears it, so the next /publish succeeds.

Decision

6S3 storage

  • Content-addressed blobs: plugins/{pluginId}/blobs/{sha256}. Immutable, never overwritten, deduplicated. The sha is the identifier the editor and Runtime pass around.
  • Exactly two files per branch — one client, one server. No multi-file plugins. This removes the files[0] ambiguity for good.
  • No consumer of code ever receives a presigned URL — not the editor, not Runtime, not the browsers of chat members running the plugin's cl.js. Code travels inline through Registry in both directions (§7, §10), so authorisation is checked per request and there is no TTL to race.
  • The presigned two-phase upload stays — but only for icons, screenshots, and any future release bundles, where files are larger and uploaded once.

The sha-based identifier also settles two earlier questions at once: the "one-time link" question disappears (no link), and the optimistic-concurrency check on save (§10) is just a sha comparison.

File size & request compression

Limit: 500 KB — 500 000 bytes of UTF-8 — per file, measured on the decoded text string after any transfer decoding. Over → 413 { "error": "file_too_large", "side": "server", "limit": 500000, "actual": 812345 }.

  • The limit is on decompressed content, not wire bytes. The client may send Content-Encoding: gzip (or br); Gateway and Registry decode first, then measure. Compression shrinks the upload — it does not raise the ceiling.
  • Decompression is itself bounded to defuse a zip bomb: the request is rejected with 413 as soon as the decoded stream passes 1.2 MB (two 500 KB files + base_sha + JSON framing + headroom)2.2 MB. JSON escaping inflates source text before it can be measured: \n, \" and \\ take 2 bytes each, so two legal 500 KB files can occupy up to 2 MB of JSON; the rest covers base_sha, framing and headroom. Clients must send non-ASCII as raw UTF-8, not \uXXXX escapes (the JSON.stringify default); a body that escapes it anyway may hit the cap early and gets the same 413, whatever Content-Length claims, and a decoded/encoded ratio over ~200 trips the same guard.
  • The editor shows a live byte counter per pane and blocks Save locally at the limit; the 413 is the server-side backstop.

What 500 KB actually buys

On the wire, source text gzips ~3–5× (Brotli ~4–6×), so a file at the limit uploads as roughly 100–150 KB.

7Runtime: reload & state

Branch resolution — the client never sends branch_id

POST /command only ever carries { name, pluginId, chatId, trackId, args }. The plugin's own frontend (the DSL running in the browser) neither knows nor sends a branch id — the same trust boundary as identity (§3): a chat cannot pick which code runs against it. Runtime resolves (pluginId, chatId) → branch_id itself:

  • cache Map<(pluginId, chatId), branchId>, TTL 60 s — a plain timeout rather than push-based invalidation, since a stale entry only matters for the rare case of an uninstall or a version switch, and the cost of being wrong for up to a minute (one command runs against the previous branch) is low;
  • on a miss, Runtime calls GET installation-service /internal/installations/resolve?plugin_id=&chat_id= → { branch_id, branch_status }.

This cache is independent of the engine cache below and untouched by reload — a hot-reload never changes which branch is installed, only the code inside it.

Engine cache

Map<(pluginId, branchId), LuaPluginEngine>. No sha in the key. Runtime never executes client code, so client_blob_sha was never a legitimate part of this key — a client-only edit used to force a pointless rebuild. A RELEASED branch running in many chats and the author's dev branch are different cache entries — neither clobbers the other. Plugin state stays keyed by (pluginId, chatId) in Redis and is swapped in via changeContext before each command.

One function loads an engine, used everywhere an entry is missing — a cold cache after a Runtime restart is not a special case. GET /code/serverGET /internal/plugins/{id}/code/server — Registry's service-to-service route: not exposed through the Gateway and not gated by user — returns the source inline (§10) — no presigned URL, no second hop to S3; Registry does that read itself:

loadEngine(pluginId, branchId):
  if cache.has((pluginId, branchId)): return cache.get(...)
  { text, sha } = GET registry /plugins/{pluginId}/code/server/internal/plugins/{pluginId}/code/server?branch_id={branchId}
  engine = compile(text)
  cache.put((pluginId, branchId), engine)
  return engine

Reload

POST /internal/plugins/{pluginId}/reload { chat_id, branch_id } — called by Registry only when the server side changed. A client-only save (JS edited, Lua untouched) never reaches Runtime at all — there is nothing for it to reload, since it doesn't execute client code in the first place. Runtime evicts (pluginId, branchId) and immediately re-invokesrebuilds (pluginId, branchId) through the same fetch-and-compile body of loadEngine above to rebuild it — not an inlined copy of the new code. The old engine keeps serving commands until the new one has compiled; then a single cache.put() swaps it in, so there is no window in which a concurrent command compiles a second copy. Two reasons:

  • One pipeline, not two. If reload instead carried the code inline, "engine came from a reload" and "engine came from a cold cache miss" would be different code paths that can silently drift apart (e.g. after a Runtime restart, the cache is empty and every engine is rebuilt through loadEngine — if reload had its own inline path, that path would go untested until the one moment it matters).
  • Free GC for the mutable branch. The dev branch keeps the same branch_id forever, so reload is a plain cache.put() on a key that already exists — the old LuaPluginEngine is simply dereferenced and left to the JVM. Nothing to track, no orphaned shas to sweep. A RELEASED branch's branch_id never reloads at all (its code is frozen); its cache entry only ever leaves via ordinary idle/LRU eviction.

Redis state is preserved across a reload and passed through the built-in auto-migrator. Minimum interval 3 s per (plugin, chat)(plugin, branch) — the unit that actually gets rebuilt, so switching chat_id cannot bypass it → 429 { retry_after_ms }. The auto-migrator runs eagerly for the chat_id in the request (skipped if that chat no longer has the plugin installed); every other chat on the same branch is migrated lazily, before its next command runs on the new engine. The response is just { "reloaded": true } — Runtime never touches client code, so it has no opinion on client_changed; Registry already knows that from the save it just performed and reports it itself (§10, §11).

A throttled reload is not lost. If the save's reload call gets 429, the new code is already stored but the engine is stale, and a later save with an unchanged server side would not reload it. Registry returns reloaded: false with retry_after_ms; once that delay has passed, the editor calls the explicit hot-reload endpoint POST /api/v1/plugins/{id}/branches/{bid}/reload (§10). The Hot-reload button uses the same endpoint, which always forwards to Runtime whether or not the code changed.

Net effect on a save's internal call count (§10, §14 have the numbers): a client-only edit never involves Runtime at all — just the S3 write plus the fstick.plugin.reloaded push, since other open editor tabs still needevery client running that dev branch still needs to know to re-fetch cl.js. A server-only edit skips that push (§11) but pays for the write, the reload call, and the now single-hop code fetchthe internal code fetch, and Registry's S3 read behind it. Only an edit that touches both sides pays for everything.

State editing

The editor's JSON state panel is editable; Runtime applies it. PUT /api/v1/plugins/{id}/state?chat_id=, author + dev-branch install only. Full JSON (not a patch). Invalid JSON → 400. Otherwise the payload runs through the auto-migrator and schema validation, leniently: missing fields defaulted, unknown keys dropped, type mismatches coerced — written to Redis, discrepancies returned as warnings, then the normal broadcast fires. No optimistic lock — state changes on every command, so a hash guard would almost always conflict; the panel gets a refresh button instead. The schema is the plugin's own SetStateSchema / state_schema declaration (backend_stdlib.lua). The migrator is a new stdlib function MigrateState; it also runs before every command, which migrates the other chats lazily.

8Console streaming

The print/warn hooks fire inside command execution, where Runtime knows pluginId, branchId, chatId, and the calling user — all as internal_uuid. The console line must reach the plugin author, and no one else.

Path — batched

  1. Runtime takes the author's internal_uuid straight from GET registry /plugins/{id}/internal/plugins/{id} (the author_id field — no MXID anywhere; the public route would return 404 for a dev-only plugin, since Runtime is not the author) and caches it in its own small map, Map<pluginId, authorId> — independent of the engine cache (§7) and untouched by reload, since the author never changes with the code.
  2. Runtime buffers print/warn lines and POSTs them in batches to integration /api/v1/plugin-console as { author_id, msgs: [ … ] } — flushed on a ~100 ms timer, when the buffer hits 64 lines, or when the command returns, whichever is first.
  3. integration resolves internal_uuid → mxid once, drops any line for a chat_id the author is no longer a member of, wraps the array into a single fstick.plugin.console event { msgs: [ … ] }, and calls Dendrite /events/push. The client appends every msgs[] entry to the console pane in order.

Kept separate from broadcastPluginState — console traffic is bursty and single-recipient. One resolve, one push, N lines. This is why the mapper sits in integration: the one service that already turns internal ids into Matrix pushes does the resolution, and Runtime never handles an MXID.

Levels & the system flag

  • level: "info" | "warn" | "error". Lua gets two output hooks now: print(msg) → info, and a new warn(msg) → warn. Both are the plugin's own output, so system: false.
  • system: boolean says who produced the line. false — the plugin's own code called print/warn. true — Runtime generated it itself: an uncaught Lua exception, a load-time syntax error, or a flood-protection notice. System lines are level: "error" today (nothing else triggers one yet), but the flag is independent of level so a future Runtime advisory (e.g. "approaching state size limit") can ship as warn without being mistaken for the author's own output.
  • The editor renders system: true lines visually distinct from the author's own print/warn output (different left rule / icon), so a crash doesn't read like something the plugin printed on purpose.

Flood protection

  • Per line: message truncated at 8 KB with a …[truncated] marker.
  • Per batch: at most 256 lines; overflow is dropped and replaced by one synthetic { level: "error", system: true, message: "N console lines dropped (rate limit)" }.
  • Per (plugin, chat): a token bucket (≈500 lines / 10 s). Sustained flooding drops with the same synthetic marker rather than backing up the buffer.

Gateway

Swap the inbound X-User-Id — an MXID set by Dendrite — to internal_uuid via integration /api/v1/identity/resolve, cached in-process (LRU, no invalidation). Forward only that; X-User-Matrix-Id is not propagated. Proxy the new routes: …/branches/{bid}/edit, …/branches/{bid}/code, /publish, the moderation actions, PUT …/state, ?owned=true, …/branches/{bid}/reload, …/branches/{bid}/cancel, GET /moderation/branches, …/code/client, PATCH /installations/{id}; serve GET /api/v1/me itself. Never proxy /internal/**.

Response enrichment. On the way out the Gateway adds an MXID next to every user id it recognises: author_id → author_mxid, installed_by → installed_by_mxid, claimed_by → claimed_by_mxid, author.id → author.mxid. Values come from its cache or lookup-batch. Services never store or return MXIDs themselves.

10Endpoint contracts

Conventions

  • Every external call goes through the Gateway with Authorization: Bearer <matrix_token>. The Gateway authenticates it and injects X-User-Id: <internal_uuid> (§3); contracts below are the logical shape at the service boundary.
  • Error body is always { "error": "<snake_code>", "message": "<human>", … }. Codes: 400 malformed, 401 bad token, 403 not the author / not a moderator on something the caller can see, 404 unknown id or branch not visible to the caller — a hidden branch is always 404, never 403, so its existence does not leak, 409 state conflict, 413 too large, 422 semantic validation, 429 throttled.
  • The transition actions (claim / approve / reject / cancel) are idempotent on retry: a repeat that finds the branch already in the target state returns 200 with the current row; an action invalid for the current state returns 409. So a repeated reject on a REJECTED branch is 200, while reject on a CANCELLED or RELEASED branch is 409.
  • Routes under /internal/** are service-to-service only: never proxied by the Gateway, not gated by X-User-Id, reachable only on the internal network.
  • "Moderator" means a row in registry.moderators (§4).

12Frontend contract

  • Edit shows when installation.branch_status === "WORKING" and installation.author_id === myInternalUuid; myInternalUuid comes from GET /api/v1/me, fetched once per session.
  • Editor surface: two code panes (client / server), a console pane that appends each msgs[] entry of a fstick.plugin.console event (filtered by plugin_id + chat_id, info/warn/error toggle), and a collapsible editable JSON state panel with a refresh button.
  • Console lines with system: true render visually distinct from the plugin's own print/warn output — a crash shouldn't look like something the author printed.
  • Each code pane shows a live byte counter and blocks Save at 500 KB; the server 413 is the backstop.
  • Two views: the right-hand panel, and a separate window opened with window.open on the same origin — auth token read from localStorage, same as the Matrix sessionthe child window gets the access token from its opener over postMessage (origin-checked) instead of reading storage directly. Element may keep the token encrypted with a pickle key in IndexedDB, so its storage layout is not a contract.
  • Save holds the sha pair from GET …/edit, sends them as base_sha; on 409 it tells the user the code changed elsewhere and to reload.
  • Hot-reload button is debounced to ≥ 3 s and handles 429. It calls POST …/branches/{bid}/reload. After a save that returned reloaded: false, the editor calls it automatically once retry_after_ms has passed.
  • On fstick.plugin.reloaded with client_changed, re-fetch cl.js (GET …/code/client?branch_id=&chat_id=) and re-run runDsl — in every client that has the plugin active in that chat, not only in the editor.
  • A brand-new debug plugin opens with template code and a template icon.
  • The author is shown as @localpart — strip :domain from the MXID*_mxid field the Gateway adds; never render the full MXID or the internal UUID.
  • When a candidate branch is pending (WAITING_APPROVE / APPROVING), the plugin's management view shows its status and a Cancel submission action (POST …/branches/{bid}/cancel).
  • Users in registry.moderators get a review view: the queue, candidate code (read-only, via code/client and code/server), and claim / approve / reject.

Contradictions and gaps fixed in this revision. In the text, new wording is highlighted with its tag, removed wording is struck through, and new blocks carry a new label. The changes button (top right) hides all of it for a clean read.

Overview

1Scope & the editor loop

The editor lets a plugin author edit both halves of an installed debug plugin in place, push changes to the running Runtime without reinstalling, and watch backend print output from the chat they opened the editor in.

From the original user story:

  • A plugin has states: debug / release.
  • Only the author can install a debug plugin; it never appears in the public marketplace.
  • An installed debug plugin shows an Edit button.
  • The editor renders in two places: the right-hand panel (where the marketplace lives) and a separate window.
  • The editor is two text fields (Lua, JS) plus a debug console that prints backend output from the chat the editor was opened from.

Nothing about state inspection, multi-file plugins, or a build step is in scope. Code is exactly two files: one client, one server.

Decision · mapper in integration-service

3Identity model

The core stores one pure UUID per user and nothing else. The uuid ↔ mxid mapper lives in integration-service — the one component that already speaks Matrix. An MXID appears on exactly two hops: inbound (Dendrite → Gateway) and outbound (integration → Dendrite).

The :domain suffix cannot leave the Matrix wire protocol without forking away from federation — it is structural (event sender, room membership, routing). The domain is fixed to one constant and simply not rendered; Element already speaks MXIDs, so showing @user_id is a trim, not a new identifier.

internal_uuid

9f3c1a2e-…
the only id in the core

The foreign key in every Fstick service: plugins.author_id, installations.installed_by, branch owner. Never leaves the backend, never reaches Dendrite.

MXID

@ilya:fstick.local → @ilya
Matrix's own id

Dendrite's: sender, membership, tokens, event push. Frontend renders the localpart only; the domain is one fixed constant. The Matrix display name is untouched — a label, not an identifier.

The mapper

  • Table in integration-service: internal_uuid (PK) ↔ mxid (unique). Bidirectional. No handle, no profile layer.
  • POST /api/v1/identity/resolve  { mxid } → { internal_uuid } — create-or-return, idempotent. This is where a user's internal_uuid is minted, on first contact.
  • GET /api/v1/identity/{internal_uuid}  → { mxid } — the reverse, for outbound push. Batch variant for member lists.
  • Gateway calls resolve to turn the X-User-Id Dendrite gave it (an MXID) into internal_uuid, then forwards that. Result cached in-process — the binding never changes, so the cache is an LRU with no invalidation. X-User-Matrix-Id is not propagated; nothing past the Gateway needs it.
  • registry.plugins.author_id = internal_uuid (column is already UUID). Delete resolveAuthorId() / nameUUIDFromBytes.

Why Postgres, not just Redis

Gateway keeps a Redis or in-process cache either way. The question is the system of record, and that has to be Postgres:

  • It is source of truth, not derived data. Every plugins.author_id and installations.installed_by FK is an internal_uuid that only has meaning through this table. A cache you can rebuild from upstream; this table is upstream. Lose it to an eviction or a flush and every ownership record is orphaned.
  • Durability. Redis persistence (RDB/AOF) is lossy by design — snapshot intervals, fsync windows. Postgres gives real ACID + WAL: a committed identity stays committed.
  • Atomic idempotency. resolve must mint exactly one internal_uuid even when the same new user fires two requests in parallel. UNIQUE(mxid) + INSERT … ON CONFLICT DO NOTHING RETURNING does this in one statement. In Redis it is a hand-rolled SETNX/Lua dance with edge cases.
  • Queries. First-seen audit, admin lookups, batch member resolution, later handle history if it ever comes back — all relational. Redis answers exact-key GET and nothing else without hand-built secondary indexes.

So: Postgres is the system of record; Redis (or the Gateway's own map) is an optional read cache in front of it — invalidation-free, because the mapping is immutable.

Cost

integration-service is stateless today (a pure Dendrite ACL — no datasource). This gives it its first table. And the Gateway now depends on integration to authorise any uncached request: cached users survive an integration outage, brand-new users get 503. integration is already on the critical path (installation-service calls it for membership), so this is not a new failure class — but it is a wider blast radius. See §13.

Decision · git-shaped model

4Versioning: branches & content-addressed blobs

A plugin's code lives on branches. A save writes an immutable, content-addressed blob. Publishing forks a candidate branch. REJECTED and CANCELLED are branch statuses, not global states.

GitFstick
working branch (dev)the plugin's debug copy — one per plugin, owned by the author
commiteach editor save / hot-reload phase 2
create a candidate branchPOST /plugins/{id}/publish — snapshots the dev branch's current blob pair
branch statusWAITING_APPROVE APPROVING RELEASED REJECTED CANCELLED — on the branch
main / release taga branch with status RELEASED; installs resolve to the highest SemVer among them

Data model — phase 1 (no commit history)

-- one row per plugin
branches (
  id, plugin_id,
  status            -- WORKING (dev) | WAITING_APPROVE | APPROVING | RELEASED | REJECTED | CANCELLED
  semver            -- null on the dev branch
  client_blob_sha, server_blob_sha,
  runtime_client, runtime_server   -- e.g. cl.js@1.0.0 / sv.lua@1.0.0 (stdlib version)
  base_branch_id,   -- dev branch a candidate was cut from
  reject_reason,    -- set on REJECTED only; null for CANCELLED
  created_at, updated_at
)

-- content-addressed, immutable, deduplicated
S3: plugins/{plugin_id}/blobs/{sha256}
  • Exactly two blobs per branch (client + server). The client-supplied filename is discarded.
  • The dev branch's blob shas are its HEAD; a save replaces them (old blobs become GC candidates — see §13).
  • An installation references a branch. A debug install points at the dev branch and follows its shas. A normal install points at a RELEASED branch, re-pointed via PATCH.
  • Public marketplace list: plugins with status = ACTIVE and at least one RELEASED branch. GET /plugins?owned=true returns the caller's own plugins including dev-only ones.
  • Legacy plugins with arbitrary key names keep the files[0] fallback until backfilled.

Phase 2, when diff / revert / history is wanted: add a commits table. Blobs are already content-addressed, so it lands with no data migration.

Decision · explicit actions

5Moderation lifecycle

The author works on the dev branch. Publishing cuts a candidate branch into a review queue. A rejection (moderator) or a cancellation (author) leaves a dead branch — the author goes back to the dev branch and publishes again.

On reject

  • Branch status = REJECTED, retained (hidden, never in the queue, never installable).
  • plugins.last_rejection = { reason, at, semver, branch_id } — so the UI shows "needs changes" without scanning chat.
  • A plugin_moderation_log row is appended.
  • A message is sent to the author in a system room (“Fstick Developer”) via Integration — delivery, not the record of truth.

On cancel

  • The author withdraws their own candidate from WAITING_APPROVE or APPROVING: POST /plugins/{id}/branches/{bid}/cancel.
  • Branch status = CANCELLED, retained as a tombstone (hidden, not in the queue, not installable).
  • No last_rejection, no bot-room message — nothing was wrong. A plugin_moderation_log row is still appended for the trail.
  • If a moderator had already claimed it (APPROVING), it just disappears from their queue.
Guard

POST /publish returns 409 if the plugin already has a non-terminal candidate (WAITING_APPROVE or APPROVING). One open candidate at a time — a rejection or a cancellation clears it, so the next /publish succeeds.

Decision

6S3 storage

  • Content-addressed blobs: plugins/{pluginId}/blobs/{sha256}. Immutable, never overwritten, deduplicated. The sha is the identifier the editor and Runtime pass around.
  • Exactly two files per branch — one client, one server. No multi-file plugins. This removes the files[0] ambiguity for good.
  • The editor never receives a presigned URL. Code travels inline through Registry, so authorisation is checked per request and there is no TTL to race.
  • The presigned two-phase upload stays — but only for icons, screenshots, and any future release bundles, where files are larger and uploaded once.

The sha-based identifier also settles two earlier questions at once: the "one-time link" question disappears (no link), and the optimistic-concurrency check on save (§10) is just a sha comparison.

File size & request compression

Limit: 500 KB — 500 000 bytes of UTF-8 — per file, measured on the decoded text string after any transfer decoding. Over → 413 { "error": "file_too_large", "side": "server", "limit": 500000, "actual": 812345 }.

  • The limit is on decompressed content, not wire bytes. The client may send Content-Encoding: gzip (or br); Gateway and Registry decode first, then measure. Compression shrinks the upload — it does not raise the ceiling.
  • Decompression is itself bounded to defuse a zip bomb: the request is rejected with 413 as soon as the decoded stream passes 1.2 MB (two 500 KB files + base_sha + JSON framing + headroom), whatever Content-Length claims, and a decoded/encoded ratio over ~200 trips the same guard.
  • The editor shows a live byte counter per pane and blocks Save locally at the limit; the 413 is the server-side backstop.

What 500 KB actually buys

ContentBytes / char≈ characters≈ lines
ASCII code (typical)1500 0008 000 – 16 000
heavy Cyrillic comments / strings2~250 0004 000 – 8 000
emoji-dense4~125 000—

Line counts assume 30–60 characters per line including indentation and the newline. For reference, a large single source file in Element itself runs 2 000–3 000 lines — a 500 KB Lua or JS file is far outside anything the two-pane editor targets. On the wire, source text gzips ~3–5× (Brotli ~4–6×), so a file at the limit uploads as roughly 100–150 KB.

Decision

7Runtime: reload & state

Engine cache

Map<VersionKey, LuaPluginEngine> where VersionKey = (pluginId, client_blob_sha, server_blob_sha). A RELEASED branch running in many chats and the author's dev branch are different cache entries — neither clobbers the other. Plugin state stays keyed by (pluginId, chatId) in Redis and is swapped in via changeContext before each command.

Reload

POST /internal/plugins/{pluginId}/reload — called by Registry after a save. Evicts the entry for (pluginId, shas) so the next command in that chat rebuilds it; Redis state is preserved and passed through the built-in auto-migrator. Minimum interval 3 s per (plugin, chat) → 429 { retry_after_ms }.

State editing

The editor's JSON state panel is editable; Runtime applies it. PUT /api/v1/plugins/{id}/state?chat_id=, author + dev-branch install only. Full JSON (not a patch). Invalid JSON → 400. Otherwise the payload runs through the auto-migrator and schema validation, leniently: missing fields defaulted, unknown keys dropped, type mismatches coerced — written to Redis, discrepancies returned as warnings, then the normal broadcast fires. No optimistic lock — state changes on every command, so a hash guard would almost always conflict; the panel gets a refresh button instead.

Decision

8Console streaming

The print hook fires inside command execution, where Runtime knows pluginId, branchId, chatId, and the calling user — all as internal_uuid. The console line must reach the plugin author, and no one else.

Path — batched

  1. Runtime takes the author's internal_uuid straight from GET registry /plugins/{id} (the author_id field — no MXID anywhere) and caches it in the engine entry, keyed by (pluginId, shas).
  2. Runtime buffers print lines and POSTs them in batches to integration /api/v1/plugin-console as { author_id, msgs: [ … ] } — flushed on a ~100 ms timer, when the buffer hits 64 lines, or when the command returns, whichever is first.
  3. integration resolves internal_uuid → mxid once, wraps the array into a single fstick.plugin.console event { msgs: [ … ] }, and calls Dendrite /events/push. The client appends every msgs[] entry to the console pane in order.

Kept separate from broadcastPluginState — console traffic is bursty and single-recipient. One resolve, one push, N lines. This is why the mapper sits in integration: the one service that already turns internal ids into Matrix pushes does the resolution, and Runtime never handles an MXID.

Flood protection

  • Per line: message truncated at 8 KB with a …[truncated] marker.
  • Per batch: at most 256 lines; overflow is dropped and replaced by one synthetic { level: "error", message: "N console lines dropped (rate limit)" }.
  • Per (plugin, chat): a token bucket (≈500 lines / 10 s). Sustained flooding drops with the same synthetic marker rather than backing up the buffer.

10Endpoint contracts

Conventions

  • Every external call goes through the Gateway with Authorization: Bearer <matrix_token>. The Gateway authenticates it and injects X-User-Id: <internal_uuid> (§3); contracts below are the logical shape at the service boundary.
  • Error body is always { "error": "<snake_code>", "message": "<human>", … }. Codes: 400 malformed, 401 bad token, 403 not the author / not a moderator, 404 unknown id or branch not visible to the caller, 409 state conflict, 413 too large, 422 semantic validation, 429 throttled.
  • The transition actions (claim / approve / reject / cancel) are idempotent on retry: a repeat that finds the branch already in the target state returns 200 with the current row; an action invalid for the current state returns 409.

12Frontend contract

  • Edit shows when installation.branch_status === "WORKING" and installation.author_id === myInternalUuid.
  • Editor surface: two code panes (client / server), a console pane that appends each msgs[] entry of a fstick.plugin.console event (filtered by plugin_id + chat_id, info/error toggle), and a collapsible editable JSON state panel with a refresh button.
  • Each code pane shows a live byte counter and blocks Save at 500 KB; the server 413 is the backstop.
  • Two views: the right-hand panel, and a separate window opened with window.open on the same origin — auth token read from localStorage, same as the Matrix session.
  • Save holds the sha pair from GET …/edit, sends them as base_sha; on 409 it tells the user the code changed elsewhere and to reload.
  • Hot-reload button is debounced to ≥ 3 s and handles 429.
  • On fstick.plugin.reloaded with client_changed, re-fetch cl.js and re-run runDsl.
  • A brand-new debug plugin opens with template code and a template icon.
  • The author is shown as @localpart — strip :domain from the MXID; never render the full MXID or the internal UUID.
  • When a candidate branch is pending (WAITING_APPROVE / APPROVING), the plugin's management view shows its status and a Cancel submission action (POST …/branches/{bid}/cancel).

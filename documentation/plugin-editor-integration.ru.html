Обзор

1Задача и цикл редактора

Редактор позволяет автору плагина править обе части установленного debug-плагина на месте, доставлять изменения в работающий Runtime без переустановки и видеть вывод бэкендного print из того чата, где редактор был открыт.

Из исходного user story:

  • У плагина есть состояния: debug / release.
  • Debug-плагин может установить только автор; в публичном магазине его нет.
  • У установленного debug-плагина есть кнопка Edit.
  • Редактор показывается в двух местах: в правой панели (где магазин) и в отдельном окне.
  • Редактор — это два текстовых поля (Lua, JS) плюс консоль отладки, которая выводит бэкенд-вывод из того чата, откуда редактор был открыт.

Инспекция состояния, мМногофайловые плагины и шаг сборки — вне рамок. Код — ровно два файла: один клиентский, один серверный. Инспекция состояния входит в рамки: у редактора есть редактируемая JSON-панель состояния для чата, из которого он открыт (§7, §12). История состояния, diff и брейкпоинты — нет.

3Модель идентичности

Ядро хранит один чистый UUID на пользователя и ничего больше. Маппер uuid ↔ mxid живёт в integration-service — единственном компоненте, который уже говорит на Matrix. MXID появляется ровно на двухтрёх хопах: вход (Dendrite → Gateway) и, выход (integration → Dendrite) и обогащение ответа (Gateway → клиент, чтобы UI мог показать @localpart).

Суффикс :domain нельзя убрать из проводного протокола Matrix без форка от федерации — он структурен (sender события, membership комнаты, роутинг). Домен фиксируется одной константой и просто не рендерится; Element и так говорит MXID-ами, так что показ @user_id — это обрезка, а не новый идентификатор.

Не покидает бэкенд, не доходит до Dendrite.Для клиента непрозрачен: может приходить в ответах API и в GET /api/v1/me, чтобы фронтенд мог сравнивать id, но никогда не рендерится и не доходит до Dendrite.

Маппер

  • Таблица в integration-service: internal_uuid (PK) ↔ mxid (unique). Двунаправленная. Ни handle, ни профильного слоя.
  • POST /api/v1/identity/resolve  { mxid } → { internal_uuid } — create-or-return, идемпотентно. Здесь internal_uuid пользователя минтится при первом контакте.
  • GET /api/v1/identity/{internal_uuid}  → { mxid } — обратное, для исходящего push. Batch-вариант для списков участников. Batch-варианты в обе стороны: resolve-batch (mxid → uuid: списки участников) и lookup-batch (uuid → mxid: обогащение ответов в Gateway).
  • Gateway вызывает resolve, чтобы превратить X-User-Id, который дал Dendrite (это MXID), в internal_uuid, и форвардит уже его. Результат кэшируется в процессе — связка не меняется, поэтому кэш это LRU без инвалидации. X-User-Matrix-Id не прокидывается; за Gateway он никому не нужен. Gateway также держит обратную мапу (uuid → mxid) и обогащает ею ответы на выходе.
  • registry.plugins.author_id = internal_uuid (колонка уже UUID). Удалить resolveAuthorId() / nameUUIDFromBytes.
  • GET /api/v1/me → { internal_uuid, mxid } — отдаёт сам Gateway из кэша маппера; единственный источник собственного internal_uuid для фронтенда (§12).
  • Installation-service по-прежнему зовёт integration для проверки членства в чате, но теперь передаёт internal_uuid; integration сам переводит его в MXID перед запросом к Dendrite.

Без миграции

Продовой базы и легаси-плагинов нет. Схемы переписываются на месте — plugins.author_id с первой строки хранит internal_uuid, installations.installed_by становится UUID — а локальные тома пересоздаются. Ни бэкфилла, ни путей совместимости.

Почему Postgres, а не только Redis

Кэш (Redis или в процессе) Gateway держит в любом случае. Вопрос в системе-источнике истины, и она обязана быть Postgres:

  • Это source of truth, а не производные данные. Каждый FK plugins.author_id и installations.installed_by — это internal_uuid, который имеет смысл только через эту таблицу. Кэш можно восстановить из источника; эта таблица и есть источник. Потеря на вытеснении или flush осиротит каждую запись о владении.
  • Долговечность. Персистентность Redis (RDB/AOF) лоссова по дизайну — интервалы снапшотов, окна fsync. Postgres даёт настоящий ACID + WAL: закоммиченная идентичность остаётся закоммиченной.
  • Атомарная идемпотентность. resolve должен заминтить ровно один internal_uuid, даже когда тот же новый пользователь шлёт два запроса параллельно. UNIQUE(mxid) + INSERT … ON CONFLICT DO NOTHING RETURNING делает это одним запросом. В Redis это рукописный танец SETNX/Lua с краевыми случаями.
  • Запросы. Аудит первого появления, admin-поиск, batch-резолв участников, позже история handle, если она вернётся — всё реляционное. Redis отвечает на GET по точному ключу и больше ни на что без рукописных вторичных индексов.

Итого: Postgres — система-источник истины; Redis (или собственная мапа Gateway) — необязательный read-кэш перед ней — без инвалидации, потому что маппинг неизменяем.

Цена

integration-service сегодня stateless (чистый ACL к Dendrite — без датасорса). Это даёт ему первую таблицу. И Gateway теперь зависит от integration при авторизации любого некэшированного запроса: кэшированные пользователи переживут падение integration, совсем новые получат 503. integration и так на критическом пути (installation-service зовёт его за membership), так что нового класса отказа нет — но радиус поражения шире. См. §13.

Решение · явные действия

5Жизненный цикл модерации

Автор работает на dev-ветке. Публикация вырезает ветку-кандидат в очередь ревью. Отказ (модератор) или отмена (автор) оставляет мёртвую ветку — автор возвращается на dev-ветку и публикует снова.

При reject

  • Кто может отклонить: из WAITING_APPROVE — любой модератор; из APPROVING — только взявший claim (то же правило, что и для approve).
  • Ветка status = REJECTED, сохраняется (скрыта, никогда в очереди, никогда не устанавливается).
  • plugins.last_rejection = { reason, at, semver, branch_id } — чтобы UI показывал «нужны правки» без скана чата.
  • Дописывается строка в plugin_moderation_log.
  • Автору отправляется сообщение в системную комнату («Fstick Developer») через Integration — доставка, не источник истины.

При cancel

  • Автор отзывает собственного кандидата из WAITING_APPROVE или APPROVING: POST /plugins/{id}/branches/{bid}/cancel.
  • Ветка status = CANCELLED, сохраняется как тумстоун (скрыта, не в очереди, не устанавливается).
  • Ни last_rejection, ни сообщения в бот-комнату — ничего не было не так. Строка в plugin_moderation_log всё равно дописывается для истории.
  • Если модератор уже взял её (APPROVING), она просто исчезает из его очереди.
Ограничение

POST /publish возвращает 409, если у плагина уже есть нетерминальный кандидат (WAITING_APPROVE или APPROVING). Один открытый кандидат за раз — отказ или отмена его снимают, следующий /publish проходит.

6Хранилище S3

  • Content-addressed блобы: plugins/{pluginId}/blobs/{sha256}. Неизменяемые, никогда не перезаписываются, дедуплицированы. sha и есть идентификатор, которым обмениваются редактор и Runtime.
  • Ровно два файла на ветку — один клиентский, один серверный. Многофайловых плагинов нет. Это навсегда убирает неоднозначность files[0].
  • Ни один потребитель кода не получает presigned URL — ни редактор, ни Runtime, ни браузеры участников чата, исполняющие cl.js плагина. Код идёт инлайн через Registry в обе стороны (§7, §10), так что авторизация проверяется на каждый запрос и нет TTL, с которым надо гонки.
  • Двухфазная presigned-загрузка остаётся — но только для иконок, скриншотов и будущих release-бандлов, где файлы крупнее и грузятся один раз.

Идентификатор на основе sha заодно закрывает два прежних вопроса: вопрос «одноразовой ссылки» исчезает (ссылки нет), а проверка оптимистичной конкурентности при сохранении (§10) — это просто сравнение sha.

Размер файла и сжатие запроса

Лимит: 500 КБ — 500 000 байт UTF-8 — на файл, замеряется на раскодированной строке text после любого transfer-декодирования. Больше → 413 { "error": "file_too_large", "side": "server", "limit": 500000, "actual": 812345 }.

  • Лимит на распакованный контент, не на байты в проводе. Клиент может слать Content-Encoding: gzip (или br); Gateway и Registry сначала декодируют, потом меряют. Сжатие уменьшает загрузку — потолок оно не поднимает.
  • Декомпрессия сама ограничена, чтобы обезвредить zip-бомбу: запрос отклоняется с 413, как только раскодированный поток проходит 1.2 МБ (два файла по 500 КБ + base_sha + JSON-обвязка + запас)2.2 МБ. JSON-экранирование раздувает исходник ещё до замера: \n, \" и \\ занимают по 2 байта, так что два легальных файла по 500 КБ могут занять до 2 МБ JSON; остальное — base_sha, обвязка и запас. Клиент обязан слать не-ASCII сырым UTF-8, а не \uXXXX (поведение JSON.stringify по умолчанию); тело с таким экранированием может упереться в лимит раньше и получит тот же 413, что бы ни утверждал Content-Length; отношение decoded/encoded больше ~200 триггерит тот же guard.
  • Редактор показывает живой счётчик байт в каждом поле и блокирует сохранение локально на лимите; 413 — серверный бэкстоп.

Решение

7Runtime: reload и состояние

Резолв ветки — клиент никогда не шлёт branch_id

POST /command несёт только { name, pluginId, chatId, trackId, args }. Собственный фронтенд плагина (DSL в браузере) не знает и не шлёт id ветки — та же граница доверия, что и для идентичности (§3): чат не должен выбирать, чей код исполнится. Runtime сам резолвит (pluginId, chatId) → branch_id:

  • кэш Map<(pluginId, chatId), branchId>, TTL 60 с — обычный таймаут, а не push-инвалидация, потому что протухшая запись имеет значение только в редком случае деинсталла или смены версии, а цена ошибки на минуту-другую (одна команда выполнится на прежней ветке) низкая;
  • на промахе Runtime зовёт GET installation-service /internal/installations/resolve?plugin_id=&chat_id= → { branch_id, branch_status }.

Этот кэш независим от кэша движка ниже и не трогается reload’ом — hot-reload никогда не меняет, какая ветка установлена, только код внутри неё.

Кэш движка

Map<(pluginId, branchId), LuaPluginEngine>. Sha в ключе нет вообще. Runtime никогда не исполняет клиентский код, поэтому client_blob_sha в ключе не имел права быть с самого начала — правка только клиента вызывала бессмысленную пересборку. RELEASED-ветка, работающая во множестве чатов, и dev-ветка автора — разные записи кэша, ни одна не затирает другую. Состояние плагина по-прежнему кэшируется по (pluginId, chatId) в Redis и подставляется через changeContext перед каждой командой.

Загрузка движка — одна функция, используется везде, где записи нет; холодный кэш после рестарта Runtime — не особый случай. GET /code/serverGET /internal/plugins/{id}/code/server — служебный маршрут Registry: не выставлен через Gateway и не проверяет пользователя — отдаёт исходник инлайн (§10) — ни presigned-ссылки, ни второго хопа в S3; это чтение делает сам Registry:

Reload

POST /internal/plugins/{pluginId}/reload { chat_id, branch_id } — вызывается Registry, только если менялась серверная сторона. Чисто клиентское сохранение (правили JS, Lua не трогали) до Runtime вообще не доходит — ему нечего перезагружать, он и так этот код не исполняет. Runtime вытесняет (pluginId, branchId) и тут же заново вызывает ту же loadEngine выше, чтобы пересобратьпересобирает (pluginId, branchId) тем же телом «скачать и скомпилировать» из loadEngine выше — а не получает инлайн-копию нового кода. Старый движок обслуживает команды, пока новый не скомпилирован; затем один cache.put() подменяет его, так что нет окна, в котором параллельная команда скомпилировала бы вторую копию. Две причины:

  • Один пайплайн, а не два. Если бы reload нёс код инлайн, «движок из reload» и «движок из холодного промаха кэша» были бы разными путями кода, которые могут незаметно разойтись (например, после рестарта Runtime кэш пуст и каждый движок собирается через loadEngine — если у reload был бы свой инлайн-путь, он оставался бы непроверенным до момента, когда это станет критично).
  • Бесплатная сборка мусора для мутируемой ветки. У dev-ветки один и тот же branch_id навсегда, так что reload — это обычный cache.put() по уже существующему ключу — старый LuaPluginEngine просто теряет ссылку и достаётся JVM. Ничего отслеживать, никаких осиротевших sha подметать не нужно. branch_id у RELEASED-ветки вообще никогда не reload’ится (код заморожен); её запись в кэше уходит только обычным idle/LRU-вытеснением.

Состояние в Redis сохраняется через reload и проходит через встроенный авто-мигратор. Минимальный интервал 3 с на (plugin, chat)(plugin, branch) — ту единицу, которая реально пересобирается, так что сменой chat_id его не обойти → 429 { retry_after_ms }. Авто-мигратор работает сразу для chat_id из запроса (пропускается, если в этом чате плагин уже не установлен); остальные чаты на той же ветке мигрируются лениво, перед их следующей командой на новом движке. Ответ — просто { "reloaded": true } — Runtime никогда не трогает клиентский код, поэтому ему нечего сказать про client_changed; Registry уже знает это из сохранения, которое сам только что выполнил, и сообщает сам (§10, §11).

Отложенный throttle-ом reload не теряется. Если вызов reload при сохранении получил 429, новый код уже записан, но движок устарел, и следующее сохранение без изменений серверной стороны его не перезагрузит. Registry возвращает reloaded: false с retry_after_ms; когда задержка пройдёт, редактор зовёт явный эндпоинт hot-reload POST /api/v1/plugins/{id}/branches/{bid}/reload (§10). Им же пользуется кнопка Hot-reload; он всегда пробрасывает вызов в Runtime, независимо от того, менялся ли код.

Итог по числу внутренних запросов на одно сохранение (полные контракты в §10): чисто клиентская правка вообще не задействует Runtime — только запись в S3 и push fstick.plugin.reloaded, потому что другим открытым вкладкам редакторакаждому клиенту, исполняющему эту dev-ветку, всё равно нужно узнать, что надо перекачать cl.js. Чисто серверная правка этот push пропускает (§11), но платит за запись, вызов reload и теперь однохоповый запрос кода, внутренний запрос кода и стоящее за ним чтение S3 в Registry. Правка обеих сторон платит за всё.

Редактирование состояния

JSON-панель состояния в редакторе редактируемая; Runtime её применяет. PUT /api/v1/plugins/{id}/state?chat_id=, только автор + установка на dev-ветке. Полный JSON (не патч). Невалидный JSON → 400. Иначе payload проходит через авто-мигратор и валидацию по схеме, лениво: недостающие поля добираются дефолтами, неизвестные ключи отбрасываются, несовпадения типов коэрсятся — пишется в Redis, расхождения возвращаются в warnings, затем срабатывает обычный broadcast. Оптимистичной блокировки нет — состояние меняется на каждой команде, так что hash-guard почти всегда конфликтовал бы; вместо него у панели кнопка «обновить». Схема — собственное объявление плагина SetStateSchema / state_schema (backend_stdlib.lua). Мигратор — новая функция stdlib MigrateState; она также выполняется перед каждой командой, так что остальные чаты мигрируются лениво.

Решение

8Стриминг консоли

Хуки print/warn срабатывают внутри исполнения команды, где Runtime знает pluginId, branchId, chatId и вызывающего пользователя — всё как internal_uuid. Строка консоли должна дойти до автора плагина и ни до кого больше.

Путь — батчами

  1. Runtime берёт internal_uuid автора прямо из GET registry /plugins/{id}/internal/plugins/{id} (поле author_id — никакого MXID; публичный маршрут вернул бы 404 для dev-only плагина, ведь Runtime не автор) и кэширует его в собственной мелкой мапе Map<pluginId, authorId> — отдельно от кэша движка (§7) и не тронутой reload’ом, поскольку автор не меняется вместе с кодом.
  2. Runtime буферизует строки print/warn и POST-ит их батчами в integration /api/v1/plugin-console как { author_id, msgs: [ … ] } — flush по таймеру ~100 мс, при достижении 64 строк или при возврате команды, что раньше.
  3. integration резолвит internal_uuid → mxid один раз, отбрасывает строки тех chat_id, где автор больше не участник, оборачивает массив в одно событие fstick.plugin.console { msgs: [ … ] } и вызывает Dendrite /events/push. Клиент добавляет каждый элемент msgs[] в панель консоли по порядку.

Отдельно от broadcastPluginState — трафик консоли бёрстовый и одному получателю. Один резолв, один push, N строк. Именно поэтому маппер сидит в integration: единственный сервис, который уже превращает внутренние id в Matrix-push, делает и резолв, а Runtime никогда не трогает MXID.

Уровни и флаг system

  • level: "info" | "warn" | "error". У Lua теперь два хука вывода: print(msg) → info, и новый warn(msg) → warn. Оба — собственный вывод плагина, поэтому system: false.
  • system: boolean говорит, кто породил строку. false — код плагина сам вызвал print/warn. true — строку сгенерировал сам Runtime: неперехваченное исключение Lua, синтаксическая ошибка при загрузке или уведомление защиты от флуда. Сегодня системные строки всегда level: "error" (больше пока нечему её вызвать), но флаг независим от уровня, чтобы будущее предупреждение от Runtime (например, «приближение к лимиту размера состояния») могло идти как warn, не выдавая себя за собственный вывод автора.
  • Редактор рендерит строки с system: true визуально отдельно от собственного вывода автора через print/warn (другая левая полоса / иконка), чтобы падение не читалось как то, что плагин напечатал намеренно.

Защита от флуда

  • На строку: message обрезается на 8 КБ с маркером …[truncated].
  • На батч: максимум 256 строк; переполнение отбрасывается и заменяется одной синтетической { level: "error", system: true, message: "N console lines dropped (rate limit)" }.
  • На (plugin, chat): token bucket (≈500 строк / 10 с). Постоянный флуд отбрасывается тем же синтетическим маркером, а не копит буфер.

Соглашения

  • Каждый внешний вызов идёт через Gateway с Authorization: Bearer <matrix_token>. Gateway его аутентифицирует и проставляет X-User-Id: <internal_uuid> (§3); контракты ниже — это логическая форма на границе сервиса.
  • Тело ошибки всегда { "error": "<snake_code>", "message": "<human>", … }. Коды: 400 невалидный запрос, 401 плохой токен, 403 не автор / не модератор для того, что вызывающий видит, 404 неизвестный id или ветка не видна вызывающему — скрытая ветка всегда 404, никогда 403, чтобы не выдавать её существование, 409 конфликт состояния, 413 слишком большой, 422 семантическая валидация, 429 throttled.
  • Действия-переходы (claim / approve / reject / cancel) идемпотентны при повторе: повтор, который находит ветку уже в целевом состоянии, возвращает 200 с текущей строкой; действие, невозможное для текущего состояния, возвращает 409. То есть повторный reject на REJECTED-ветке — 200, а reject на CANCELLED- или RELEASED-ветке — 409.
  • Маршруты /internal/** — только service-to-service: Gateway их никогда не проксирует, X-User-Id не проверяется, доступны только во внутренней сети.
  • «Модератор» — это строка в registry.moderators (§4).

12Контракт фронтенда

  • Edit показывается, когда installation.branch_status === "WORKING" и installation.author_id === myInternalUuid; myInternalUuid берётся из GET /api/v1/me, раз за сессию.
  • Поверхность редактора: два поля кода (client / server), панель консоли, которая добавляет каждый элемент msgs[] события fstick.plugin.console (фильтр по plugin_id + chat_id, тумблер info/warn/error), и сворачиваемая редактируемая JSON-панель состояния с кнопкой «обновить».
  • Строки консоли с system: true рендерятся визуально отдельно от собственного вывода плагина через print/warn — падение не должно выглядеть как то, что напечатал автор.
  • Каждое поле кода показывает живой счётчик байт и блокирует сохранение на 500 КБ; серверный 413 — бэкстоп.
  • Два вида: правая панель и отдельное окно, открываемое через window.open на том же origin — токен авторизации читается из localStorage, как у Matrix-сессиидочернее окно получает access token от opener по postMessage (с проверкой origin), а не читает хранилище напрямую. Element может хранить токен зашифрованным pickle-ключом в IndexedDB, так что его раскладка хранилища — не контракт.
  • Сохранение держит пару sha из GET …/edit, шлёт их как base_sha; на 409 сообщает пользователю, что код изменён в другом месте, и просит обновить страницу.
  • Кнопка hot-reload дебаунсится до ≥ 3 с и обрабатывает 429. Она зовёт POST …/branches/{bid}/reload. После сохранения с reloaded: false редактор сам вызывает его, когда пройдёт retry_after_ms.
  • По fstick.plugin.reloaded с client_changed — перекачать cl.js (GET …/code/client?branch_id=&chat_id=) и перезапустить runDsl — в каждом клиенте, где плагин активен в этом чате, а не только в редакторе.
  • Совсем новый debug-плагин открывается с шаблонным кодом и шаблонной иконкой.
  • Автор показывается как @localpart — отрезать :domain от MXIDполя *_mxid, которое добавляет Gateway; никогда не рендерить полный MXID или внутренний UUID.
  • Пока ветка-кандидат висит (WAITING_APPROVE / APPROVING), в панели управления плагином виден её статус и действие Отменить заявку (POST …/branches/{bid}/cancel).
  • Пользователи из registry.moderators получают экран ревью: очередь, код кандидата (только чтение, через code/client и code/server) и claim / approve / reject.
